# Approved low-bit Metal TensorOps research plan

> Versioned record of [issue #1](https://github.com/kaaburgh/apple-matrix-capabilities/issues/1), accepted 2026-10-25 and incorporating review rounds 1–4 before repository publication.
>
> For the first hands-on tasks see [PHASE-0.md](PHASE-0.md). Measurement methodology and existing receipts remain governed by [METHODS.md](../../METHODS.md). No on-device validation is implied by committing this plan.

## Goal / scope

Investigate **how Apple Silicon M5/M5 Max (and, as a comparison, M6) execute low-bit matrix operations**: FP16/BF16, INT8/INT4, FP8 E4M3/E5M2, FP4 E2M1 and B-scaled variants. Reuse Precisit's existing Metal TensorOps probes instead of building another benchmark framework. Determine which tested paths exercise **Neural Accelerators (NAs)**, what their performance limiters are, and whether observed differences are consistent with conversion/dequantization overhead.

**Evidence boundaries (non-negotiable):**
- `API-supported`: the selected Metal/MLX path compiles and executes, and its output passes the **upstream intended-value correctness check**. Until independent format-semantics tests exist, this does **not** establish full FP4/FP8 numerical correctness; for packed inputs only the discovered nibble order has been checked.
- `measured-performance`: rate for a specified kernel, toolchain, shape, tile and measurement protocol.
- `NA-active`: supported by a calibrated hardware counter at a documented scope.
- `native-format-plausible`: an *inference* supported by controlled ablations and discriminating counters, with alternative explanations listed.
- **Physical ISA instruction identified: OUT OF SCOPE for v1.** Neither similar throughput nor NA utilization alone proves a native FP4/FP8 instruction. A 0% or missing counter is not proof of nonuse without calibration.

**Status:** revised research plan for review; no implementation started. Hardware-dependent steps are **blocked until a suitable Apple Silicon machine and profiling toolchain are available**. Do not substitute simulated/CPU tests for on-device evidence.

### Reuse policy and sources

- Keep `probes/lane_sweep.py`, `probes/integer_lanes.py`, `probes/geometry_sweep.py`, `probes/_common.py`, `tools/build_matrix.py`, original `receipts/` and baseline `matrix/` data.
- Use **stock MLX** (pip wheel or a **debug build of the same upstream tag**, if needed); do not depend on Precisit's experimental MLX fork.
- Existing `receipts/` are immutable historical evidence; do **not** silently change stock probe defaults, overwrite past results or reinterpret their `vs_f16` ratios as controlled format ablations.
- The existing float and integer probes have different timing methods. A new *controlled comparison* runner may reuse their kernels, but must not replace the published upstream protocol.
- [Upstream METHODS](https://github.com/precisit/apple-matrix-capabilities/blob/main/METHODS.md) · [MLX Metal Debugger](https://ml-explore.github.io/mlx/build/html/dev/metal_debugger.html) · [Apple M5 GPU profiling tech talk](https://developer.apple.com/videos/play/tech-talks/111432/)

- [ ] On **the actual device**, separately inspect **Instruments / Metal System Trace** and **Xcode Metal Debugger**. - [ ] Test what `xctrace` can really collect and export in a documented, machine-readable format; a `.gputrace` replay is **not** interchangeable with Instruments `.trace` or `xctrace export`.
- [ ] Check whether the stock MLX **wheel** provides sufficient shader source attribution and Metal Debugger statistics. If not, try `-DMLX_METAL_DEBUG=ON` on the **same upstream MLX version**; record that build, and later compare its uncaptured performance to the wheel.
- [ ] Name the initial calibration controls: **positive:** `f16*f16->f32` using TensorOps; **negative:** FP16 GEMM using `simdgroup_matrix` (Apple's non-NA V1 example), where supported. For the Phase 0a spike it may be a small local standalone shader, but keep its source, SHA-256, correctness results and launch configuration with the experiment manifest. If retained for Phase 2, add it as a named, independently validated control in PR A (or preserve its local source and hash explicitly); never treat an unidentified third-party screenshot as a control. Treat absence of a usable NA counter as a documented blocker, not as a zero reading.

**Go/no-go:** only proceed to a reusable capture/profiling tool if the trace opens, the target dispatch is identifiable **and at least one useful profiling signal is observable**. If not, explicitly revise the issue to a **capture-only/blocked architecture study** with reproducible details. No full infrastructure until feasibility is demonstrated.

## Phase 0b — baseline and convergence validation (uncaptured; disposable experimental script)

**Ordering resolution:** PR B's reusable comparison runner does **not** exist yet. Phase 0b uses a **small disposable local script/manual harness** invoking existing probe functions; the reusable convergence and batching primitives belong in **PR A** because its `--loop` mode also needs them. The complete controlled comparison runner and INT8 adapter remain in PR B. No dependency on a later PR is permitted for a phase gate. Keep controlled convergence / T(N) observations and exploratory manifests under **local, gitignored `experiments/<chip>/`**, never in `receipts/` (which accepts only upstream receipt schemas). New receipts are valid **only** when an unmodified upstream probe actually produced them. Keep the disposable script locally with a SHA-256 and explicit configuration. **Publish the reviewed, sanitized disposable-script source** (e.g. a small versioned GitHub file or gist, not just its hash) so others can inspect and re-run Phase 0b; verify there are no local paths or secrets first. **Post a sanitized Phase 0b summary + the source link and SHA-256 in this issue**, including the convergence settings, selected N, fitted `a` and `b` with uncertainty, and test-device/toolchain identity. The script may be disposable as maintained product code, **not as evidence provenance**.

A review of `receipts/m5-max/lane_sweep_v3.json` found a consistent first-sample-to-last-sample ramp (91/100 series have the slowest first sample; median first/min ratio ≈1.80). Existing M5 Max best-of-five float rates and tile rankings therefore **cannot be assumed converged**. The cause (GPU frequency/power-state ramp, host overhead, or another factor) is a **hypothesis** to test, not established fact.

- [ ] Run `python -m unittest discover -s tests`, `tools/build_matrix.py --check` and selected existing probes; save **new upstream-format receipts** (with pinned toolchain) instead of altering historical ones. Record **disposable-script timing outputs separately** under local `experiments/<chip>/`; do not try to validate them as receipts. Note: `lane_sweep.py` has no check-only CLI; use a small `--lanes` subset (it still times) or validate separately in the disposable script.
- [ ] For a new *controlled timing path*, validate inputs/output **before** timed work. Keep NumPy reference calculations and other CPU work out of timed/alternating GPU samples.
- [ ] For **uncaptured throughput** and Instruments `--loop` runs, use a **time-based warm-up with a bounded convergence test**, e.g. `>=0.5 s` back-to-back GPU work and the last three recent windows within ~2%; parameterize criterion and max budget, record duration and `converged=true/false`. If it does not converge, report it and do not select a purported steady-state tile. **Do not require steady-state convergence before `--capture`**: for a Metal Debugger replay, pre-capture warm-up only needs to complete JIT/pipeline compilation and first-touch allocations. GPU performance state during the subsequent Xcode *replay* is independent of pre-capture warm-up; never mark a `.gputrace` as `converged`.
- [ ] Measure batches of **N = 1, 2, 4, 8, 16** independent dispatches per synchronization; fit `T(N) = a + b·N` with uncertainty. Report `a` as an *effective fixed cost* and `b` as **back-to-back throughput**, **not** single-dispatch GPU latency: MLX may overlap independent calls and host/queue costs contribute. **Guard allocations:** each call creates a new output array; keep `N × output_bytes` below the applicable MLX cache/memory limits (typically a 2 GiB cache limit on 32+ GB machines), or lower N and record why. A standard 2048×4096 f32 output is 32 MiB, hence N=16 needs 512 MiB of outputs; some large geometries exceed this budget. Cross-check with GPU-side timing/counters when available.
- [ ] Run **interleaved replicated A/B trials** (`A B A B …`) after warm-up, no NumPy/CPU validation between samples; report median, sample distributions, spread and order sensitivity, not only best-of-five.
- [ ] Specify the original machine's **exact SKU**: the published M5 Max baseline is **40 GPU cores / 128 GB**. A different M5 Max GPU-core or memory configuration is **not the same observed chip row**. For new published receipts use a distinct chip/SKU key and receipts directory, per CONTRIBUTING; compare like-for-like **within-chip normalized ratios** and label cross-SKU absolute-GOPS comparisons as non-equivalent.
- [ ] Check GPU performance-state/frequency and thermal behavior during uncaptured warm-up, if exposed. Optional **`sudo powermetrics --samplers gpu_power`** can collect GPU frequency/residency; it requires **explicit machine-owner approval** for sudo, and only that sampler should be requested. Do not collect/publish default process-list samplers. Document missing telemetry rather than infer a mechanism.
- [ ] **Do not time** in capture/debug modes: refuse the controlled timing/`--loop` path when `MTL_CAPTURE_ENABLED`, `MTL_DEBUG_LAYER`, `MTL_SHADER_VALIDATION` or `METAL_DEVICE_WRAPPER_TYPE` is enabled/set in a way that can alter performance; record the effective state of these flags. Consider a **separate small upstream-compatible change** recording such environment state in future stock receipts, without rewriting old receipts.

**Gate:** report a converged or explicitly nonconverged FP16 control at the target geometry and tile, with repeatable uncaptured timing *when convergence succeeds*. Publish a **sanitized baseline summary, reviewed script source link and script SHA-256** in this issue before selecting PR A's default warm-up threshold and batch N. A nonconverged run is a diagnostic baseline, **not** a steady-state rate or a reason to choose an optimal tile. If the ramp persists, create **a separate upstream issue** with evidence; do not silently 'fix' upstream defaults.

Use a **`sources` SHA-256 map**, as upstream receipts do: a single capture-tool SHA is inadequate because the actual shader is generated by `lane_sweep.py` (or its integer counterpart). Capture an MLX debug-build-vs-wheel comparison when applicable. **Never describe a captured trace or replay as 'converged'.**

- [ ] Use **existing lane names** as the capture CLI input, deriving layout, `relaxed_precision` and scaling from `LANES` and `lane_relaxed()`. Do **not** expose independent `--scaled` / `--relaxed` flags that silently create unrepresented lanes. The existing integer probe's global `--relaxed` is a separate, explicit adapter parameter and must be recorded.
- [ ] Rediscover packed nibble order (`lo` first, `hi` only on failed check) and verify against any cited receipt's `packing`. New experimental lanes without an existing receipt must be labelled **exploratory / not receipt-matched** and cannot silently claim receipt provenance.

Control the precision flag, matrix layout, scaling and output semantics to the degree feasible. Mark unavoidable mismatches, e.g. INT8 `→i32` vs FP16 `→f32`.
- [ ] Do not directly compare `integer_lanes.py` best-of-batch rates to `lane_sweep.py` single-call best rates as a clean arithmetic effect. Obtain controlled same-protocol measurements before such a claim.

## PR A — isolated float-lane capture and Instruments loop (first code milestone)

Initially support **existing `lane_sweep.py` lanes only**: `f16*f16->f32` plus one FP8 and one FP4 lane **and both `f32*f32->f32` / `strict_f32*f32->f32` controls** to calibrate a precision-mode/arithmetic-path change before INT8 exists. INT8 needs a distinct `integer_lanes.py` adapter and comes later because function signatures and operand preparation differ. Ensure the float controls are correctness-checked just like the primary lanes.

- [ ] Add a small `probes/capture_lane.py` (name provisional) that **reuses** `lane_sweep.LANES`, `build()`, `encoded_operands()`, `reference()`, `call()` instead of duplicating Metal shaders. Follow `geometry_sweep.py` import conventions; the import calls `cap_memory()` and intentionally inherits upstream allocator limits. **Record** these limits; do not change upstream memory behavior implicitly.
- [ ] Implement explicit **capture** lifecycle: **prepare inputs → independently validate/reference-check → short JIT/pipeline/first-touch warm-up → synchronize → start capture → target dispatch(es) + `mx.eval()` → stop capture**. **The capture does not inherit or prove a steady-state GPU clock.** Xcode Metal Debugger performance numbers are from **replay**, not the recording run; record Xcode replay settings and compare replay times only against same-configuration replays. Keep large check-stage arrays and their GPU operations outside the capture window; release temporary check data and optionally clear the MLX cache before capture, without freeing the actual target inputs.
- [ ] Provide **two mutually exclusive modes**:
  1. `--capture`: one bounded target dispatch (N=1 by default), explicit count if N>1, fresh non-existing `.gputrace` path; catch failures and always stop an active capture.
  2. `--loop SECONDS`: **uncaptured**, bounded convergence-tested warm-up followed by **batches of N independent dispatches per `mx.eval`** (e.g. N=8 based on the Phase 0b T(N) result), with no host synchronization after every single dispatch; clear idle gaps before and after to locate the window in **Metal System Trace**. Record N, batch duration and **GPU idle fraction from the timeline** beside NA utilization, since per-dispatch host gaps disproportionately penalize faster lanes. If the warm-up reaches its time budget without convergence, **the loop may still run as a diagnostic** but must record `converged=false` and must **not contribute to steady-state throughput claims or tile selection**. Never treat this run as Metal Debugger replay timing; obey output-memory budget.
- [ ] Verify that Xcode actually shows the expected `amc_…` shader and expected number of dispatches, with no unexpected benchmark/validation operations in the capture. Do not assume N independent dispatches serialize; document possible overlap.
- [ ] Require `MTL_CAPTURE_ENABLED=1` in `--capture` and a **new output path**; refuse incompatible debug/capture flags in `--loop`. Document how to launch each mode with a minimal environment and open traces.
- [ ] Record a **minimal human-readable local manifest** (not a new public schema): lane/shape/tile/packing/precision, dispatch/batch count, `sources` SHA-256 map (capture script + actual shader generator + `_common.py`), MLX tag/wheel-vs-debug build, macOS/Xcode/SDK, allocator settings, capture vs loop mode, environment, **replay settings (when relevant)** and observed metric scope. For loop results record convergence and GPU idle fraction; for capture/replay **do not** record a `converged` claim. Do **not** write this under `receipts/`.
- [ ] Keep old `receipts/`, `matrix/`, and upstream benchmark semantics unchanged. Add `capture_lane.py` to `.github/workflows/check.yml` `py_compile` and AGENTS.md compilation list. Reuse the Phase 0b test configuration in PR A and **cross-check the FP16 control**: the reusable converged throughput and fitted T(N) slope `b` should agree with Phase 0b within a **predeclared ±5%** under the same device/toolchain/power conditions (or have statistically overlapping repeat-run uncertainty); otherwise investigate and record the discrepancy before accepting PR A. Preserve the original Phase 0b summary as a reviewable comparator.
- [ ] Add CPU/stub tests: existing output path is refused; missing `MTL_CAPTURE_ENABLED` rejected; failed/incorrect check never starts capture; `stop_capture` runs on exception; output never enters `receipts/`; timing mode rejects capture/debug/validation env; mode selection and manifest are deterministic. Add explicit tests that **`N × output_bytes` exceeding the memory/cache budget is refused or N is reduced with a recorded reason**, **capture/replay manifests never assert a `converged` field**, **`--loop` manifests record N and batch duration**, and a failed warm-up is labelled `converged=false` and excluded from steady-state result selection. Use an opt-in **real Apple GPU** smoke test for actual trace validity.

**Acceptance:** correctly checked FP16, FP8/FP4 and relaxed/strict FP32 examples can be captured/replayed with identifiable target dispatch and **recorded Xcode replay settings**; an **N-batched**, uncaptured `--loop` window is visible in Instruments with measured idle fraction (steady-state claims only when `converged=true`); **FP16 steady-state rate and T(N) slope reproduce Phase 0b within the predeclared ±5% or overlapping uncertainty** under comparable conditions; all existing tests/validators pass; historical results unchanged. No steady-state claim is derived from GPU replay.

## Phase 2 — counter calibration and hypothesis-driven profiling (manual gate)

Define predictions **before** reading counters; use only counters that distinguish known controls. An NA activity counter may indicate acceleration without distinguishing native FP8 from a converted FP16 path.

- [ ] Identify/capture **Neural Accelerator utilization**, **instruction mix** (when exposed), **Performance Limiters**, memory/cache and GPU performance-state data **with their exact collection scope**.
- [ ] Calibrate first using **named positive/negative controls** and **available float-only same-chip contrasts**, rerun under the converged protocol: (a) FP16 TensorOps lane, tiles such as `64x32x4` vs `64x64x2`; (c) B-scaled E4M3 at `64x64x4` vs `64x128x4` **on the currently available chip** (M5 Max initially; repeat on M6 if available). Published M6 (≈1.62×) and M5 Air (≈1.33×) ratios are candidates to verify, **not** substitutes for local measurements; M5 Max old ratios may contain warm-up bias.
- [ ] **New float arithmetic-path control (d), available before INT8:** compare `f32*f32->f32` against `strict_f32*f32->f32` using the same source template/types/layout/tile, changing only `relaxed_precision`. Prior receipts show ≈**1.6–2.4×** relaxed/strict at **`64x128x4` or `128x128x8`** (chip-dependent), with some other tiles showing **inverted ratios**. Re-measure under the converged protocol, restrict initial controlled calibration to those two specified tiles and **investigate/report inversions as findings, not dismiss them as noise**. Do **not** presuppose the direction of NA utilization: relaxed f32 could round to a lower-precision representation and run on NAs while strict f32 uses shader ALU, **or** strict f32 could also use NAs with multiple split-precision passes. These yield different counter predictions. Build an **independent numerical fingerprint** for the same f32 lanes using full-mantissa random operands and an FP64 reference, plus references with operands rounded to TF32 (10-bit mantissa), BF16 and FP16 before multiplication; measure how error grows with K. Keep this separate from the original probe's deliberately exactly-representable input values. Record `MLX_ENABLE_TF32` explicitly (published receipts have it `unset`). A counter that distinguishes tile throughput but not this changed precision/arithmetic mode **cannot distinguish native from converted low-bit paths (H1)**; mark it **non-discriminating for arithmetic-path questions**.
- [ ] **Defer (b) INT8 vs FP16 matched-tile calibration to PR B**, after the integer adapter exists; it is not a prerequisite for this earlier manual gate. If a counter cannot discriminate the relevant controlled contrast, mark **non-discriminating**, not proof of equivalence.
- [ ] Test hypotheses: (H1) M5 unscaled E4M3 ≈ FP16 could reflect native low-bit compute **or** hidden conversion; extra shader ALU/conversion work growing with tile K footprint would favor explicit conversion, but no such change is **not proof** of native arithmetic (conversion may occur inside the accelerator); (H2) B-scaling costs may reflect ALU scale work, memory/cache and/or NA stalls; (H3) M6's faster E4M3 path may reflect new hardware **or** different compiler/driver dispatch.
- [ ] Interpret NA utilization with **Performance Limiters** and memory behavior. Upstream kernels use raster threadgroup traversal and a dynamic-K `op.run`; lower NA% can result from cache locality, memory throughput, scheduling or frequency rather than format emulation. Consider a Morton/swizzled control only **later**, after confirming counters are useful.
- [ ] Keep raw `.gputrace` and `.trace` local. Manually document reproducible profiler actions, **Xcode replay/profiling configuration** and derived values; do not specify an automated exporter without proving it exists. Distinguish counters measured during an Instruments live loop from statistics produced by **Metal Debugger replay**.

**Gate:** a written report on which counters are observable, which discriminate controls, and what remains unknown. Zero, missing, system-wide-only and genuinely per-dispatch observations must remain distinct.

## Phase 3 — controlled format ablations and cross-generation comparisons

**Terminology correction:** current `DEFS_SCALED` scales **operand B only** with one UE8M0 scale per 32 elements along K (`tensor_blockwise<tensor_plane_scales, …, 32, 1>`). These lanes are **B-scaled (UE8M0, 32×1 along K)**, **not a demonstration of full OCP MXFP4×MXFP4 or MXFP8×MXFP8**. Preserve upstream lane IDs (`mx_...`) for compatibility, but use precise descriptive labels in findings.

- [ ] Add missing **named, opt-in experimental lanes** in a **separate PR before relying on their captures**: `t_fp4*fp4`, `strict_fp4*fp4`, `relaxed_mx_fp4*fp4`, corresponding `f16*fp4` mixed controls, `relaxed_mx_e5m2`, and `t_f16*f16` (use exact full `->f32` names when implemented). Define a one-factor-at-a-time ablation chain for layout, packing, scales and relaxed precision; do not assume the suggested list is complete until inspected.
- [ ] **Preserve old defaults and seeds while correctly supporting experimental receipts:** keep a stable **`LANES`** base table (the existing 20 lanes, in their original order), add **`EXPERIMENTAL_LANES`**, and create **`ALL_LANES = {**LANES, **EXPERIMENTAL_LANES}`** with append-only/frozen seed indices (`LANE_INDEX`). Audit and update **every** `LANES[`, `in LANES` and `ls.LANES` site, not just an illustrative list, to use `ALL_LANES` when explicit experimental lane names are allowed. In particular cover `lane_sweep.check_tile()` and `geometry_sweep.is_packed()` (both currently index the base dictionary), alongside `lane_relaxed()`, `build()`, `encoded_operands()`, `--lanes` validation, `run_lane()`/`summarize()` and geometry_sweep's explicit-lane validation; use `list(LANES)` **only for the default requested lanes**. `summarize()` must count statuses and set `results.lanes_total` from the **actual `protocol.lanes_requested`**, not just legacy `LANES`. This is necessary because `tools/build_matrix.py` treats mismatches between the requested lanes, results and receipt coverage as **CI errors** even for uncited schema-3 receipts. Pin the **current 20 lane→seed indices** with an explicit regression test; new lanes must never change historical operands. **Replace**, do not retain unchanged, the current `test_lane_index_is_canonical_order` (`LANE_INDEX == enumerate(LANES)`), because it conflicts with an append-only `ALL_LANES` index.
- [ ] Add a CPU integration test for a **packed** experimental lane (e.g. `t_fp4*fp4->f32`) through **both** `lane_sweep.main()` and `geometry_sweep.main()` using stubbed kernels, and validate each complete receipt using **`validate_probe_receipt()`** from `tests/test_probes_cpu.py`. This must exercise packing discovery and `geometry_sweep.is_packed()`. Ensure complete experimental receipts pass `tools/build_matrix.py --check` without changing the default `lanes_requested`.
- [ ] Follow AGENTS.md: compile-check, CPU regression tests and **real-hardware correctness** for each new lane. New runs produce **new receipts**, never retroactively modify old ones. Experimental lanes must be selectable explicitly and **must not change the default `lanes_requested` or existing seeds**; any intentional protocol change requires a separately versioned decision.
- [ ] Compare **matched-tile** and **each lane's optimized tile** separately, with identical `relaxed_precision`, output semantics and layout where possible; publish per-tile ratios, uncertainty and limitations. Include FP16/BF16, INT8/INT4, both FP8 types, FP4 and mixed weight-only variants as available, rather than assuming one representation covers them.
- [ ] Separate at least four FP4 experimental paths: (1) direct packed FP4 as TensorOps operands, (2) **pre-dequantized** FP16 matmul with conversion outside timing, (3) separately timed FP4→FP16 decode + FP16 matmul, (4) fused decode+matmul if implementable. Add FP4→FP8 only if supported and useful. Report bytes moved, extra scale traffic, numeric semantics and backend path; no automatic inference of native instructions.
- [ ] Add a **separate optional format-semantics corpus** beyond upstream's exactly representable values (rounding edges, subnormals, NaNs where legal, packed ordering, scale application) with an independently decoded buffer reference. This should not modify upstream's benchmark input protocol.
- [ ] Examine additional prefill geometries and sustained loads only with converged warm-ups and consistent timing methodology. If warranted, test raster vs Morton/swizzled tile order as an independent factor (not silently mixed into format results).
- [ ] For M5 Max vs M6, prefer a genuinely matched toolchain: published receipts list **Xcode 27A266a, Metal 32023.921.6, MLX 0.32.3** on both, but **macOS builds differ**, which must be recorded and ideally controlled in new tests. Existing M5 Air/Pro results use different toolchain builds; rerun before cross-chip causal claims.

| **PR C** | Named opt-in FP4/layout/scaling ablation lanes, **merged `ALL_LANES` dispatch, pinned seeds, receipt/geometry validator coverage**, new receipts, optional conversion controls | Complete experimental-lane receipt passes the existing validator; new GPU correctness checks; no historical receipt edits |
| **PR D (conditional)** | Optional profiling sidecar schema/validator and derived-only publication | Only after counter availability/export format is verified |

**Still open for review:** actual M5 Max access and profile counter feasibility; whether the debug MLX build is necessary; which fields/counters are reliable enough to publish; scope of a possible upstream contribution. **Resolved ordering decisions:** disposable Phase 0b script before PR A; reusable warm-up/batching in PR A; INT8-specific calibration gates PR B, not Phase 2. Captures are *replayed* and are never certified as steady-state. **Proposed decisions:** keep the capture tool chip-agnostic; start with M5 Max, compare with M6 where possible; keep raw traces local; upstream only generic capture procedure/tool after validation, retaining speculative interpretation in this fork.

## Definition of done — research v1

We can reproducibly run and validate selected original lanes without changing Precisit's old measurements; obtain a converged (or explicitly nonconverged) timing baseline; capture/replay one chosen correct float and integer TensorOps dispatch; identify which *calibrated, available* NA/limiter/instruction-mix counters move under controlled changes; and publish carefully qualified, provenance-linked FP16/INT8/FP8/FP4 observations with limitations.

**Not a deliverable:** proof of a physical FP4/FP8 instruction or reverse engineering the M5/M6 ISA.
